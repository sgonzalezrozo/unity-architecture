# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

### Added

- `uiAtom` capability (`com.sgonzalezrozo.ui-atom`). With it, the `prefab` pack includes UI Atom's agent rules and UI Foundations' gradient rules, with `UIAtomAuthoring`, `UIAtomSpec`, `UIAtomValidator`, `UIGradientGroup`, `GradientShape` and `IgnoreGroupGradient` as verified symbols.
- `PREFABS.md`: with `uiAtom`, shaped backgrounds and panels are UI Atoms built with `UIAtomAuthoring` and checked with `UIAtomValidator`; an atom that is a blocking `Background` adds a transparent raycast `Image` (`PREFAB-14`); gradients are the atom's modules.

## [0.9.3] - 2026-11-25

### Added

- `CHK-02` (handoff 0.9.2 item 4): the Stop hook passes the project files changed this turn outside every feature (`CHECK_OUTSIDE_CHANGED`, from the turn mark) to `check-feature.sh`, and a change the plan's `outside-feature` line doesn't name by path fails. Without a turn mark it doesn't run. `tools/test-check-feature.sh` covers both cases.
- The project facts list the `ScreenIds` constants and their source, so a plan knows which screens exist before writing (handoff item 6). The plan reads that line before it names a screen (`planning.md`).
- `tools/test-verify-hook.sh`: runs the Stop hook with a stub `verify.sh` and checks which tests it asks for.

### Changed

- The Stop hook never runs the full suite: the periodic run (every two hours for the whole project, every 24 hours for features) is gone, with its `VERIFY_TESTS_EVERY_SECONDS` and `VERIFY_FULL_TESTS_EVERY_SECONDS` settings. A full run is started by hand, and the checklist reports it as not verified until someone runs it.
- "Solo codigo" (`code`) and code with prefabs owe no Unity unit tests (`TEST-11`): the hook runs no feature tests and no prefab validator, whatever `Logs/verify/test-scope` says, and compiles and runs the feature checks. Unknown scope keeps the scope file's tests.
- Package signatures the agent kept reading from package source are in the packs: `IScreenParameter<T>` (navigation), `BaseClickController` (ui-input), `IInstantiator` (new-feature, with the prefab section), `Forget` (code-and-verify). Each cites a section that's already in the packs.
- `ASM-02`: a reference that a package the feature uses requires (`Client.asmdef`, for example `ScreenSystem` or `UIFoundations`) is named in the plan's `outside-feature` line with its reason and needs no question. A reference the code doesn't need still asks first (`planning.md`, `FEATURE_STRUCTURE.md`).
- The Forget helper is `ToolsCore.TaskExtensions.Forget` in the Tools Core package (`com.sgonzalezrozo.core`), public and auto-referenced. `install.sh` no longer writes `Assets/Client/Shared/TaskExtensions.cs`, a copy of it; the project facts say whether the package is installed, and `CHK-17` points to the package. The Screen System copy stays internal to that package.
- `install.sh` no longer writes `Client.cs`, a comment-only file. A new project gets `Client.asmdef` alone; the features are the code, and `ScreenIds.cs` is generated by Screen System.
- The feature files table decides file names (`TASK-05`). `I{Feature}Clock.cs` is now in its exception list, which matched the table. A file the table doesn't list gets the best suggestion, named under **Table gaps** in the report, and isn't a question.
- `verify.sh` writes `startedAtUnixSeconds` in `Logs/verify/summary.json`, so a summary older than the newest script change is visibly stale. `ASM-02`: the agent adds a required package reference to `Client.asmdef` itself and names it in `outside-feature`; it never asks.
- `TASK-06`: files that exist at session start are the user's. `project-facts.md` lists the existing screens and prefabs per feature. The agent never creates, moves or deletes them, except a file the user asks to delete and confirms, which the plan names in `delete:`. `CHK-18` fails when one of them is gone without that line.
- `TASK-07`: a screen no other screen opens gets no entry point unless the request names one; the plan asks how it opens.
- `install.sh --add-instructions` (the default) keeps an existing AGENTS.md, CLAUDE.md, Copilot, Cursor and Rider file as it is and adds the rules in a block between two markers; a later install replaces only that block. `--replace-instructions` backs each file up to `<file>.bak` and writes the template. The summary says which files got the block or were replaced (`templates/scripts/instructions.sh`, `tools/test-install-instructions.sh`).
- Enforcement mode: the Stop hook reads `AI_ENFORCEMENT` or `.claude/enforcement.mode`. `advisory` (the default) reports failed checks and lets the agent finish; `enforce` sends them back and blocks the stop, as before.
- The rules install no enforcement. `install.sh` writes the rules only: AGENTS.md, CLAUDE.md, the instruction files, `.editorconfig` and the generators. `--enforcement` adds the hooks, `verify`, the checker, the timing scripts, `settings.json`, the analyzers and the first batch compile, in advisory mode; `--enforce` sets the mode that blocks. `tools/test-install.sh` checks each case on a throwaway project.
- `install.sh` asks, file by file, when a file it would write already exists and differs: a text instruction file (AGENTS.md, CLAUDE.md, Copilot, Cursor, Rider) can get the rules as a block (`a`), be replaced with a backup (`r`), or be skipped (`s`, the default). A static file (`.editorconfig`) can only be replaced or skipped. Without a terminal it does not ask: instruction files take the block (or replace with `--replace-instructions`) and static files are skipped.
- `install.sh` asks `[r]` or `[s]` for a `.claude/settings.json` that differs from the template (it can't be merged); replacing keeps the old file as `.bak`. Replacing an instruction file shows a warning first: the rules replace everything in the file that isn't the rules.
- With packs, the first step of a task is one message with a parallel `Read` of the packs it routes to and of `project-facts.md` (`AGENTS.md`), with no directory listing or `cat` first.

## [0.9.2] - 2026-11-25

Agents read less and their output is checked by a tool, the same for every model. Measured on the same requests: with task packs Opus reached its first file in 1m 38s instead of 3m 57s, and Haiku delivered the multi-source Store that passes every check for $1.13. The next steps are in `docs/plans/handoff-0.9.3.md`.

### Added

- Task packs (`OPT-07`): `scripts/ai-packs.sh` writes `Logs/ai/packs/<task>.md` from the new `packs.json`, one per kind of task (`new-feature`, `code-and-verify`, `ui-list`, `ui-input`, `navigation`, `backend`, `tests`, `prefab`). Each holds that task's rule files and sections with the forks resolved to the project's branch, the package documentation it relies on (sections of each package's `Documentation~`, chosen by hand), and a **Verified symbols** table where every symbol cites the section that documents it. Every section keeps its source and checksum, and the packs regenerate only when `packs.json`, the profile, the manifest or a source changes. AGENTS.md routes each task to its pack; the Load column stays for projects without packs. `tools/lint-rules.sh` checks every entry in every branch, that symbols cite their pack, that every rule file is in a pack, and the pack sizes.
- Project facts: `scripts/ai-facts.sh` writes `Logs/ai/project-facts.md` with the scenes in Build Settings, the Fast IoC installers, the `Client.asmdef` references, the features, and localization as three separate facts (package installed, settings configured, used by Client code), each naming its source. `csharp/style.md` says when that counts as a localization system.
- `OPT-07` asks every final report to end with `Outside packs:` and the files opened outside the packs, or `none`. The timing hook logs package reads as `pkg:<package>/<path>` (following a `cd` out of the project), and the summary shows `outside-packs` after a pack was read.
- `ui-list` includes UI Scroller's **Sources and slots** signatures and the **Bento sections** example; the symbols cite them.
- Fixed names for a feature's files (`TASK-05`): `{Feature}Main/` for a feature with one screen, `{Name}ListView` as a list's root View, `{Name}ItemData`, `{Name}SectionData`, `{Name}HeaderSlotModel`/`View`, and the prefabs. A file outside the feature is named in the plan and asked about first (`ASM-02`).
- `DI-11`: `FromInstance` takes the asset's name, never a path or a constant, and a scene installer's asset is in `Resources` or Addressables. `MODEL-12`: section titles and category names are content data unless the project has a localization system.
- Packs stay under `maxBytes` (46 KB) so one read holds them: `new-feature` is split, and `code-and-verify` holds the C# style, determinism, verification, handoff and checklist. `ai-packs.sh` warns about a pack that's too large, and the check fails on one.
- The plan has a fixed form (`PLAN-02`): `Logs/ai/plan.md`, written before any other file and shown in the approval prompt, with closed lists for each decision (where the Model lives, content data, installer, list kind, layout, input, backend, localization, changes outside the feature), the files from the Feature files table, open questions and free notes. A case the lists don't cover becomes an open question. The checklist compares the delivery with it.
- Data assets from a spec (`EDIT-14`): a feature's configuration is `Services/Resources/{Feature}Config.asset.json` (`type` and `values`), built into `{Feature}Config.asset` by `AssetSpecs` in the rules' Unity package: `Build`, `Compare` and `BuildMissing`, through the bridge, from **Assets > Unity Architecture > Build Asset From Spec**, or by `verify.sh`, which builds the missing ones in a batch run before compiling so the Fast IoC generation finds them. `verify-editor.sh` asks for missing ones. Data assets are created in every scope (`TASK-02`), in `Services/Resources/` (`DI-11`, `MODEL-12`). `AssetSpecsTests` covers it.
- The Stop summary starts with the models (with their API calls, subagents included), the API calls and the tokens of the turn, read from the session transcript, then the time, the time to the first file, the calls and rule documents before it, and the reads outside the packs.
- Where a feature's data comes from (`MODEL-12`, `MODEL-13`): runtime data (an inventory, a store's offers) comes from the backend's Module or, while there is none, from `Services/Mock{Feature}Items.cs`, a pure C# class bound in the installer; a pure C# `{Feature}ItemsModel` builds the sources in its constructor, and the screen's MonoBehaviour Model reads it injected. A configuration asset is only for designer-tunable values the request asks for. `MODEL-02`: lazy initialization in a query is a command.
- `planning.md` lists what never to ask: the language (always English, `DATA-01`), commands the request doesn't name, where data comes from, the installer, and what the project facts answer.
- The Stop hook shows one short line (time, first file, calls, outside packs, models, tokens), since the app cuts long messages; `timing-report.sh --last` prints the full summary.
- The timing summary estimates the turn's cost in USD from the transcript's tokens and the API list prices in the new `model-prices.json` (per model, cache writes at 1.25x / 2x, Haiku 5.5's long-context rate), with a model it doesn't know shown as unpriced.
- `scripts/check-feature.sh` (F5): the Stop hook checks every touched or scoped feature before compiling, with no Unity or model, so the result is the same for every agent and model: files against `Logs/ai/plan.md` (`CHK-01`), installer (`CHK-03`), specs for `FromInstance` (`CHK-04`), test assembly and no `.asmref` (`CHK-05`), the handoff's sections (`CHK-06`), namespace `Client.{Feature}` (`CHK-07`), `SectionedScroller` for a sectioned plan (`CHK-08`), every file named after the feature and a single screen folder named `{Feature}Main` (`CHK-09`), and a warning for literal lists outside the mock (`CHK-10`). A failure counts as an attempt. `TASK-05`: `{Name}` is `{Feature}` or `{Feature}{Subject}`. `tools/test-check-feature.sh` has a passing feature and one broken variant per check.
- `CHK-11`: a screen Model whenever there are Views, list and header slots, the items Model and its source, and Views never inject the items Model, mock or Module (`ROOT-06`). `CHK-12` warns about a query that builds state. Each pack lists the sources it already includes. The Stop hook fails a feature task whose final report has no `Outside packs:` line, and the Stop line names the files read outside the packs.
- The feature check runs on the task's test-scope folders (`TEST-13`), or with the whole project in scope, on the features changed since the turn began (the timing hook marks it in `Logs/verify/turn-<session>`), so another task's unfinished feature never blocks the current one.
- The checks can't be dodged by changing the plan (`CHK-13`): the first plan of a turn is kept as the approved one, and a plan that drops or adds a decision, a file or its scope after a rejection fails; the scope the user chose (read from the prompts and question answers in the transcript) wins over the plan's, and tests or prefabs outside it fail; a bento layout needs a list. `CHK-14`: every file is a row of the Feature files table. `CHK-15`: no bento layout computed in C#, and a bento plan has its JSON. Test scope, plan and attempts are kept per session (`Logs/verify/session-<session>/`). Found when Haiku passed a rejection by rewriting its plan to `list: none` and dropping the list.
- Example 04, the multi-source bento store (F7): discounts, promotions and packs as sections of one bento list, runtime data from a mock behind `StoreItemsModel`, a clock and a throttled countdown, a promotion click that opens a popup with its ID, the handoff, and the tests a scope with tests adds. It passes `check-feature.sh`. Its pack is `example-store`.
- `SCR-16`: navigation is a synchronous command on the screen's root Model, the only class that calls `ScreenManager`; a Controller is only the trigger. `CHK-16` refuses `ScreenManager` anywhere else.
- The Feature files table has a row for a clock (`I{Feature}Clock`, `{Feature}SystemClock`); test doubles live inside the test file. `TEST-13`: naming the test folder never adds tests. Moving a plan to the scope the user chose is allowed after approval, so a wrong approved scope can't deadlock a run.
- The Feature files table says that opening a screen that doesn't exist yet is an open question before writing: its `ScreenIds` constant only exists once the screen is created, so a code-only delivery can't compile.
- `install.sh` creates `Assets/Client/Shared/TaskExtensions.cs`, the project's `Forget` helper, and the project facts say whether it's there; a feature's own `Forget` fails `CHK-17`. `CHK-16` also fails a navigation call whose screen isn't a `ScreenIds` constant (`SCR-12`), so a screen that doesn't exist yet becomes a question for the user. Found when Opus opened the popup with a string and copied `Forget` into the feature.
- `verify-editor.sh` says when the last full test run started and when a script changed after it, so a stale run is clear.
- `ai-profile.sh` runs both after the profile, and with `--print` the SessionStart hook shows the profile, the facts and the packs' index.
- The timing logger resolves relative reads from the hook's `cwd`, skips heredoc bodies, resolves writes through shell variables and uses jq when it's there (a 20 KB command went from 15 s to 0.2 s). The report keeps a turn whole when a message arrives during it, and `before-first-write` counts only writes under `Assets/`.

## [0.9.1] - 2026-11-22

### Changed

- Tests compile per feature: `Assets/Client/{Feature}/Tests/Client.{Feature}.Tests.asmdef`, from a template in `FEATURE_STRUCTURE.md`, created by the agent with the feature's first test (`ASM-03`). There's no project-wide `Client.Tests` assembly or `.asmref` any more, and `install.sh` no longer creates one. To migrate, give each feature's `Tests/` folder its own `.asmdef` and delete `Assets/Client/Tests/` and the `.asmref` files.
- What a person still has to set up in Unity goes to `Assets/Client/{Feature}/IMPLEMENTATION.md`, in fixed sections (code, assets, prefabs, Inspector assignments, first run, Play mode check), and the response links it instead of repeating it (`FEAT-02`, `HAND-07`). A scope without prefabs never builds one (`TASK-02`).
- Size limits: 18 lines per method, 240 per class, 4 parameters (targets unchanged).

### Added

- Rules that make two runs of the same request build the same feature:
  - `TASK-05` and a **Feature files** table in `planning.md`: the plan's files come from it, row by row, each with its condition.
  - `TASK-04`: no command, event or file the approved plan doesn't name.
  - `MODEL-12`: content data (catalogs, starting items) comes from a configuration asset or backend JSON, never from a C# class of constants. A MonoBehaviour Model may receive an injected configuration asset.
  - `DI-11`: a feature has `{Feature}Installer` exactly when it binds something, including a configuration asset for a screen-root Model.
  - `LIST-10`: several sources in one list use `SectionedScroller` with a `SectionedSource`, one section per source.
- Timing: `.claude/hooks/log-timing.sh` logs prompts, loaded instructions, tool calls, subagents and the Stop hook's verification to `Logs/agent-timing/{session}.tsv`, with the rule documents a shell command reads, and shows each prompt's stages and seconds on screen when it ends (`AGENT_TIMING_SUMMARY=0` hides it). `scripts/timing-report.sh` prints a session step by step. No prompt text, tool arguments or file contents are logged. `install.sh` copies both, and says what to merge into an existing `settings.json`.

## [0.9.0] - 2026-11-20

### Changed

- Agents read only the rules a task needs. `MVC.md`, `UI_PATTERNS.md`, `CSHARP_STANDARDS.md` and `AGENT_WORKFLOW.md` are now short indexes of topic files in `architecture/mvc/`, `ui/`, `csharp/` and `workflow/` (the largest is 74 lines), and `AGENTS.md` routes each task straight to them. Every rule keeps its ID and text.
- Package-dependent rules are forks. Where a rule depends on a package, its topic file has a fork block with one file per branch in `architecture/branches/`: `container` (Fast IoC, another container, none), `list` (UI Scroller or not), `navigation` (Screen System or not) and `input` (UI Foundations or not). `OPTIONAL_PACKAGES.md` no longer holds every alternative: it describes the profile, the forks and the `OPT` rules. The Fast IoC parts of `DEPENDENCY_INJECTION.md` moved to the `fast-ioc` branch.
- The scope question's rules are `TASK-01` to `TASK-04`, which were `SCOPE-01` to `SCOPE-04` and clashed with the MVC scope rules of the same IDs. `SCOPE-01` to `SCOPE-05` now only mean scopes.

### Added

- `README.md`: a **Reads only what it needs** feature, the profile in the Quickstart, the SessionStart step when updating, and the lint in Contributing.
- The project profile: `scripts/ai-profile.sh` writes `Logs/ai/profile.md` from `Packages/manifest.json` and the new `capabilities.json`, with the capabilities that are true and the branch each fork resolves to. It regenerates only when the manifest, the table or a path it checks changes. `OPT-06`: agents take capabilities and forks from the profile, never from the manifest, and open only the branch it names. `install.sh` copies the script and writes the profile; a SessionStart hook in `.claude/settings.json` puts it in Claude Code's context at every session start (an existing `settings.json` is kept, and the script says what to add). The Copilot, Cursor and Rider rules point to the same file.
- `capabilities.json` is the one capability table: the profile script, the docs and the Rules Guide window read it. The window's `requires` and `<!-- if: -->` blocks accept a capability id (`fastIoC`) as well as a package name.
- `tools/lint-rules.sh`, for maintainers: every rule ID defined once, every fork listing exactly its branches with files that exist, every branch with a folder, every relative link and anchor resolving, no conditional markers in the rules, and every Rules Guide source existing. It found and fixed three broken anchors in `docs/`. `tools/test-ai-profile.sh` tests the profile script.

## [0.8.0] - 2026-11-19

### Changed

- `LIST-09` allows **New Scroll List** under `Assets/Client` when its output is the Model, View and Controller split (`{Name}ListModel`, `{Name}ItemSlotModel`...), which follows the rules and adds its assemblies to the folder's `.asmdef`. ### Added

- Windows launchers `templates/scripts/install.cmd` and `update.cmd`. They find Git Bash and run the `.sh` script with the same options, because a plain `bash` in PowerShell or cmd is WSL's launcher, which fails when no Linux distribution is installed. `.gitattributes` keeps `.sh` files LF and `.cmd` files CRLF on every checkout.
- The installation guide's troubleshooting and the Rules Guide say to add Tools Core first and wait for each package to compile: adding one while Unity is still importing another can log `ScriptableSingleton already exists` and "assets located in immutable packages were unexpectedly altered", which block nothing.

## [0.7.0] - 2026-11-19

### Changed

- Tests live next to their feature: `Assets/Client/{Feature}/Tests/`, with a `Client.Tests.asmref` that compiles them in one `Client.Tests` assembly, in the namespace `Client.{Feature}.Tests` (`ASM-03`). `install.sh` creates `Assets/Client/Tests/Client.Tests.asmdef` when the project has the Test Framework package. Tests in `Assets/Tests/` still run, but only in full runs: move them to their feature's `Tests` folder to get feature runs.

Every stop then runs the tests of those features and of every feature the change touched, and the full suite at most every 24 hours (`VERIFY_FULL_TESTS_EVERY_SECONDS`). With no scope, or a change that can affect any feature (`Shared/`, `Client.asmdef`, `Packages`, `ProjectSettings`...), it compiles and runs the full suite at most every two hours, as before. The scope file can only add tests, never skip the ones a change owes.
- The prefab validator has one case per feature folder (`ClientPrefabsTests.Inventory`, `Root` for prefabs directly in `Assets/Client`), so a changed prefab only checks its feature, and leftover errors in another feature don't block the task. With the Editor open, the reporters write `editor-prefabs-{Feature}.json` and `editor-tests-{Feature}.json`, which `verify-editor.sh` reads.
- `install.sh --help` no longer prints the script's first line of code.

## [0.6.0] - 2026-11-19

## [0.5.0] - 2026-11-19

### Added

- The Rules Guide window (**Tools > Unity Architecture > Rules Guide**) in the `.ai/unity` package: short, human-readable docs drawn from the rules, with search, shown only for the packages a project has. It no longer throws a `NullReferenceException` when it opens with the Editor, before `EditorStyles` is ready.
- `ASM-01` and `ASM-02`: all feature code compiles in `Client.asmdef`, since the analyzers, the prefab validator and the specs read only that assembly; a package already in the manifest is added to its references without approval.
- MCP for Unity is optional everywhere. `install.sh` writes `.mcp.json` only with `--mcp`, or when the manifest already has MCP for Unity (`--no-mcp` never does), so a project without it doesn't see a failed server in every session. With the Editor open and no Unity MCP, `verify-editor.sh` reports an out-of-date compile or due tests as "couldn't check" instead of a failure the agent can't fix (`VERIFY_EDITOR_BRIDGE=1` or `0` overrides the detection). **Assets > Unity Architecture > Build Prefab From Spec** builds, validates and compares a prefab from the selected spec, so specs work without a bridge. The installation guide marks MCP for Unity as optional steps.
- Usage example 6, Add a list, has two new prompts with mockups: a store with sections (`SectionedScroller`) and an events list whose cards open to show a progress bar, a reward count and an Enter or Continue button (`IExpandableSlot`). The mockups are PNGs in `docs/images/`, built by `mockups.py`, and a new tip says to attach a PNG to a prompt.
- `OPT-01` covers every use of a package or tool, not only code: prefabs, assets, menu items, wizards and code-tool calls. A rule that names one applies only when its capability is `true`; otherwise the step uses the Unity form or is left out and reported. The new menu rules and `EDIT-13` name the capability each one needs.
- Rules for the packages' new menus. `EDIT-13`: the agent doesn't run a package menu item or wizard through the bridge, since most open a window or modal dialog that blocks the Editor; it calls the code API instead. `SCR-13` names **New Screen Feature**, **Add Screen to Feature…** and **Edit Prefab** (Screen System 0.5), with `ScreenAuthoring.CreateScreen` for agents. `SCR-15`: what to do with the `Background` that **New Layer** adds, and `ScreenAuthoring.CreateLayer` for agents. `DI-09`: where a **New MonoInstaller** goes and what to add to it (Fast IoC 0.10). `DI-10`: generation runs after each compile; agents call `GenerationCoordinator.GenerateAllRetryingFailedCode()`, not **Regenerate Code**. `LIST-09`: **New Scroll List** (UI Scroller 0.7) isn't used under `Assets/Client`, because its output breaks `ARCH-02`, `-03`, `-04`, `-05` and `LIST-02`.

- `PREFAB-17`: an element with an `Action` wraps everything the `Action` hits in one `UI Content` child, the `Action`'s only sibling, so a press tween punches what was hit while the hit area stays still. A modal's close `Action` is the exception. The validator checks it, `PrefabRecipes.AddUIContent` builds it, and specs take a `uiContent` type. The validator also finds an element's `Background` inside `UI Content` for `PREFAB-14`. The diagrams in Prefabs, UI patterns, MVC, Feature structure and the three examples show the new shape; each example says how its Controllers change with `uiFoundations`.
- Prefabs says that with `uiFoundations`, click Controllers derive from `BaseClickController` (`OPT-02`), and that the `Client` assembly references `UIFoundations`. The prefab pilot had used `IPointerClickHandler` in a project with UI Foundations installed.

- `docs/INSTALLATION.md`: step by step from a new Unity project: Git, the submodule, `install.sh`, MCP for Unity and its setup (HTTP Local, the server, the **Testing** and **Scripting Extensions** tool groups, Roslyn, one registration for Claude Code), connecting Claude Code, and troubleshooting. `docs/USAGE.md`: working with Claude Code, with the Editor open or closed, twelve example prompts and what the agent does with each, and the Stop hook's messages. The README, `llms.txt` and `install.sh`'s closing steps point to them.
- Editor tools lists the MCP for Unity tools the rules use, with the tool groups that are off by default, and `execute_code`'s C# 6 fallback without Roslyn. Prefabs gives the return types of `BuildFromSpec`, `Compare` and `ValidateAsset`, and the prefab validator's test name for a filtered run.
- From the prefab pilot, where an agent built three prefabs through MCP: `PREFAB-15` (every serialized reference a Model, View or Controller declares is assigned) and `PREFAB-16` (a `Background`, `Action` or overlay inside a layout group ignores it), both checked by the validator. Specs take `fields`, which assigns serialized fields by object path, `ignoreLayout`, and Unity's UI components such as `VerticalLayoutGroup`. `AddBackground` and `AddAction` keep themselves out of a parent's layout group.
- The Stop hook checks prefabs: when a prefab under `Assets/Client` changed, it runs the prefab validator on every stop, even between test runs. With the Editor open, `verify-editor.sh` asks the agent to run it through `run_tests` and shows its errors, from `Logs/verify/editor-prefabs.json`, which the test reporter writes. With it closed, the hook runs `verify.sh` filtered to that test.
- `prefabTools` capability, `EDIT-11` (build and change prefabs only through the recipes or a spec, called through the bridge's code tool) and `EDIT-12` (validate every prefab built or changed, and compare it with its spec).
- Prefab specs (`HAND-06`): the handoff table as JSON. `PrefabSpecs.BuildFromSpec` builds it with the recipes and validates it, and `PrefabSpecs.Compare` lists every difference between a spec and its prefab. A small JSON reader in the package keeps it free of dependencies, and bad specs fail with the line, column or object to fix.
- Prefab recipes: `PrefabRecipes` in the `.ai/unity` package builds roots, screens, modals, slots, backgrounds, text, images, state roots, nested prefabs and the `Action` object already following the prefab rules, and `SaveAndValidate` checks the result. A menu item and an `-executeMethod` entry point run the validator on `Assets/Client`.
- The prefab validator (`TEST-12`): a local package in `.ai/unity`, `com.sgonzalezrozo.unity-architecture`, that `install.sh` adds to `Packages/manifest.json` and to `testables`. An EditMode test checks every prefab under `Assets/Client` for the prefab rules a tool can check, with the prefab, object and rule ID in each error. `PrefabValidator.ValidateAsset(path)` gives the same results for one prefab, through a Unity MCP server.
- `architecture/PREFABS.md` with `PREFAB-01` to `PREFAB-14`: the root's transform, anchors, pivot, TextMeshPro, no `Animator`, no persistent `UnityEvent`, `RectMask2D`, empty runtime containers, the `Action` hitbox, screen and modal shape, nested Canvases, depth, and a `Background` with raycast on that blocks touches under an element with an `Action` or a screen. `AGENTS.md` routes prefab work to it.
- `VIEW-07` and `UA0016`: a View has at most 5 serialized fields. With more, it delegates to inner Views placed near the components they set, and it serializes components and inner Views, not assets.
- Deliberate decisions in the Developer overview: where the rules differ from *Clean Code* on purpose, linked from `AGENTS.md` so agents don't "fix" them.
- `UA0015`: a `///` comment on a method, constructor, property, field, event or enum member fails the build. A class or other type may still have a short summary. It catches `///` whether or not the compiler parses documentation comments.
- Working with the Editor open, through a local Unity MCP server such as MCP for Unity (Coplay). `install.sh` writes `.mcp.json`, which registers the server on `localhost:8080`, and puts Editor scripts in `Assets/Editor/UnityArchitecture` that write every compile and test run to `Logs/verify/`. The test reporter only compiles when the Test Framework package is installed.
- `scripts/verify-editor.sh` checks the project from those results. The Stop hook uses it when the Editor is open (Unity holds `Temp/UnityLockfile`) and `verify.sh` when it's closed. It asks the agent to compile (`refresh_unity`) when a script changed after the last compile, and to run the tests (`run_tests`) when the last run started before the newest script change. It doesn't compare them with the last compile, since Unity compiles again after a test run. Script changes in local packages (`file:` entries in `Packages/manifest.json`) count too, except in folders ending in `~`.
- `EDIT-10`: with the Editor open, the agent compiles and runs the EditMode tests in the Editor before finishing.
- The Claude Code settings template allows `verify-editor.sh` and the read-only Unity MCP tools `read_console`, `refresh_unity`, `run_tests` and `get_test_job`.
- `install.sh --update` keeps a copied template you changed in your project, such as a customized hook or `verify.sh`, and lists it to merge by hand. It updates a copy only when it matches an earlier version of the template in the `.ai` repository's history, so nobody edited it. Before, it replaced any copy that differed.
- The Stop hook escapes its messages, so text with quotes or backslashes from the verify scripts stays valid JSON.

### Changed

- `OPT-04`: `OPT-02` wins over matching the code around a change; with a capability `true`, new code uses the package even where older code doesn't.
- Dependency injection says when Fast IoC's fields are ready: before `Awake` in the first scene, in scenes loaded later and in prefabs created with `IPrefabInstantiator` (Fast IoC 0.11), so Views and Controllers may use them in `Awake` and `OnEnable`.
- The C# standards say a project without a localization system uses English text until it has one (`DATA-01`).
- `INPUT-02` and `PREFAB-11`: a modal's close `Action` sits under the `Window`, which blocks touches with its own `Background`; the validator accepts it there. A modal dims with a `Background`, not a `Dimmer`, so it follows `INPUT-03`.
- The Editor reporters moved from `Assets/Editor/UnityArchitecture` to the `.ai/unity` package, so updating `.ai` updates them. `install.sh` removes the old copies nobody edited, and lists the edited ones to merge and delete by hand.
- `VIEW-03`: each scope has one root View, on its root, and only it subscribes to the Model. It may tell inner Views what to show, and they set their own components without reading the Model or subscribing. No View reaches into a nested prefab, its root View included. `UA0001` now lets a View reference a View, and still fails when a View references a Controller. `VIEW-01` applies to root Views.
- `INPUT-01`: the input object is always called `Action`, and its Controller class is named after what it does (`{Action}Controller`), whatever the hierarchy. `INPUT-03` allows a blocking `Background` with raycast on (`PREFAB-14`).
- The prefab handoff (`HAND-01`) lists pivot, scale and runtime containers too, and the examples use `Action`.
- The Stop hook only compiles on most stops. It runs the tests at most every two hours, and only when something changed since they last passed, so verifying doesn't slow down every change. `VERIFY_TESTS_EVERY_SECONDS` changes the interval, and only a full run the hook asked for counts as the last one, so filtered runs don't keep pushing it back. `verify.sh` and `verify-editor.sh` take `VERIFY_COMPILE_ONLY=1` to only compile. The full suite runs only when the hook asks for it.
- `TEST-11`: before finishing a change, the agent runs the tests directly related to it, existing and new, and they must pass. `EDIT-10` and the Definition of Done point to it. `verify.sh` takes `VERIFY_TEST_FILTER` to run only those tests with the Editor closed.

### Fixed

- The analyzers checked every assembly that references Client, not just Client: Unity hands an analyzer to those too, and Assembly-CSharp references Client automatically. In a project with code outside `Assets/Client`, every rule failed there, in third-party code and in generated code. They now check only the assembly named `Client`, so tests and the rest of `Assets` stay out, as the README already said.
- `install.sh` creates `Assets/Client/Client.asmdef` again in a new project, with a `Client.cs` note so Unity doesn't warn about an assembly definition with no scripts.
