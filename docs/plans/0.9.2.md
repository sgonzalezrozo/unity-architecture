# Plan 0.9.2: menos saltos y más consistencia, sin skills

Estado: borrador de trabajo. Base medida: [línea base 0.9.1](../benchmarks/0.9.1-inventory.md).

## Objetivo

| Problema | Medido en 0.9.1 | Meta 0.9.2 |
|---|---|---|
| Saltos de lectura | 17 a 23 llamadas y ~3,5 min antes del primer archivo | ≤ 5 llamadas y < 1,5 min |
| Consistencia | mismas decisiones, pero nombres, `FromInstance` y cambios fuera del feature distintos | dos corridas producen los mismos archivos con los mismos nombres |
| Huecos | el asset de config no se crea; cambios sin pedir en `Client.asmdef` | cada hueco lo fija una regla o lo atrapa el Stop hook |
| Medición | el logger no atribuye la mayoría de lecturas | cada lectura de reglas aparece con su documento |

Principio: las reglas siguen teniendo una sola fuente (sus archivos en `architecture/`). Lo nuevo se **genera** a partir de ellas o las **verifica** una herramienta; nunca se copia texto de una regla a otro lugar a mano.

## Orden y dependencias

```
F1 Logger preciso ──┐
                    ├─> F2 Paquetes por tarea ──> F8 Evaluación ──> F9 Release
F3 Plan con forma fija ──> F5 Verificador ──┘
F4 Assets de datos (spec + tool) ──> F5
F6 Nombres y huecos de reglas ──> F3, F5, F7
F7 Ejemplo 04
```

Primero F1 (sin él no se puede medir F2), luego F6 (fija los nombres que F3, F5 y F7 usan), después F2, F3, F4, F5, F7, y al final F8 y F9.

## F1. Logger preciso

**Por qué:** en la línea base, la mayoría de las lecturas de reglas salieron como "Shell commands", porque el agente hace `cd .ai/architecture` y después `cat mvc/views.md`. Sin atribución no se puede comprobar si los paquetes bajan las lecturas.

### Cambios

**`templates/claude/hooks/log-timing.sh`**
- Reemplazar la extracción actual (solo rutas que empiezan con `.ai/`) por una que:
  1. tome del comando todos los `cd <dir>` y todos los tokens que terminan en `.md`;
  2. resuelva cada `.md` relativo al último `cd` anterior a él en el comando;
  3. conserve solo los que caen bajo `.ai/`, `Logs/ai/packs/` o `.claude/`, normalizados a la ruta desde la raíz del proyecto (`.ai/architecture/mvc/views.md`).
- Campo nuevo en el TSV: `read_count` (número de documentos de reglas que tocó la llamada), para distinguir un `cat` de 6 archivos de uno de 1.
- Para el tool `Read`, ya funciona con `file_path`: sin cambios.
- Para escrituras por heredoc en Bash (`cat > X.cs <<EOF`), registrar el destino: buscar `> <ruta>` o `tee <ruta>` y guardarlo en `file_path` con prefijo `write:`.

**`templates/scripts/timing-report.sh`**
- Etiquetas para `Logs/ai/packs/*.md`: "Read pack new-feature", etc.
- Etiquetas para escrituras por Bash con prefijo `write:`, con la misma clasificación que `Write` (Model, View, installer...).
- Al final del resumen, una línea con métricas fijas: `before-first-write: 3m26s, 17 calls, 12 rule docs`. Es la línea que se compara entre versiones.

**`templates/claude/hooks/verify-on-stop.sh`**: sin cambios.

### Pruebas
- `tools/test-timing.sh` (nuevo): alimenta `log-timing.sh` con eventos JSON de ejemplo (un `cd` + `cat` relativo, un `cat` absoluto, un heredoc a `.cs`, un `Read`) y compara el TSV con lo esperado. Alimenta `timing-report.sh --last` con un TSV fijo y compara la salida.

### Criterio de aceptación
- Reprocesar `Logs/benchmark/0.9.1/run1` no se puede (el log viejo no tiene el comando), así que se prueba con los casos de `test-timing.sh` y con una corrida nueva: ≥ 90 % de las llamadas de lectura quedan atribuidas a un documento.

## F2. Paquetes por tarea, generados

**Por qué:** el agente recorre una cadena de documentos (AGENTS → planning → ejemplo → lists → fork → layouts → structure → DI → views → style). Un paquete con todo lo que la tarea necesita, ya con los forks resueltos, lo reduce a una o dos lecturas.

| Forma de la entrada | Significado |
|---|---|
| `architecture/mvc/models.md` | el archivo completo |
| `architecture/FEATURE_STRUCTURE.md#naming` | solo esa sección, desde su encabezado hasta el siguiente del mismo nivel |
| `fork:container/installers.md` | `architecture/branches/<rama del perfil para container>/installers.md` |
| `package:uiScroller#sections-with-headers` | esa sección del `Documentation~/agent-rules.md` del package de esa capacidad |
| `example:04` | el ejemplo, sin la parte de tests si el alcance no los incluye (se deja completo en 0.9.2) |

**`templates/scripts/ai-packs.sh`**
- Entrada: `.ai/packs.json`, `Logs/ai/profile.json` (de `ai-profile.sh`), `Packages/manifest.json`.
- Resolución de `package:`: con `file:` en el manifest, la ruta local; si no, `Library/PackageCache/<nombre>@*/Documentation~/agent-rules.md`. Si no está, la entrada se omite y el paquete lo dice en su encabezado.
- Salida: `Logs/ai/packs/<paquete>.md`, con:
  - encabezado: versión de `.ai`, perfil, hash de las fuentes, y la frase "Esto es todo lo que esta tarea necesita. Abre una fuente solo si falta algo, y dilo (`OPT-07`)";
  - cada sección precedida por `<!-- source: architecture/mvc/models.md -->`, para que los IDs sigan apuntando a su fuente;
  - los fork blocks se quitan (ya están resueltos).
- Regenera solo cuando cambia el hash de `packs.json`, de los archivos fuente o del perfil (mismo mecanismo que `input_hash` en `ai-profile.sh`).

**`templates/scripts/ai-profile.sh`**: al terminar, llama a `ai-packs.sh` si existe. Con `--print`, agrega al final la lista de paquetes disponibles (una línea cada uno), así Claude Code los ve desde el arranque de la sesión.

- Párrafo antes de la tabla: "Si `Logs/ai/packs/` existe, lee el paquete de la tarea en una sola llamada y nada más. La columna Load es para cuando no hay paquetes".

**`templates/copilot-instructions.md`, `cursor-rule.mdc`, `rider-project-rule.md`**: una línea que apunta a `Logs/ai/packs/`.

### Mantenimiento

**`tools/lint-rules.sh`**, chequeos nuevos:
- cada entrada de `packs.json` resuelve (archivo, ancla, fork con todas sus ramas, capacidad existente en `capabilities.json`);

**`tools/test-ai-packs.sh`** (nuevo, como `test-ai-profile.sh`):

### Docs

## F3. Plan con forma fija

**Por qué:** en la línea base, las decisiones salieron iguales, pero el plan era texto libre, así que no hay contra qué comparar la entrega.

### Cambios

**`architecture/workflow/planning.md`**
- Regla nueva `PLAN-02`: "El agente MUST escribir el plan en `Logs/ai/plan.md` con el formato de abajo, sin campos extra ni texto libre fuera de `Notes`, y MUST mostrarlo en la pregunta de aprobación. El verificador (`CHK-01`) compara la entrega con ese archivo".
- Reemplazar el bloque de "Plan" por el formato fijo:

```
Feature: Inventory
Folder: Assets/Client/Inventory
Scope: code | code+prefabs | code+tests | code+prefabs+tests
Test scope: Assets/Client/Inventory | project
Decisions:
  model-location: screen-root | injected          # where-a-model-lives row
  content-data: config-asset | backend | none     # MODEL-12
  installer: yes | no                             # DI-11
  list: none | scroller | sectioned               # LIST-10
  layout: none | list | grid | bento
  input: none | <Controller names>
  backend: none | module
  outside-feature: none | <paths>                 # Client.asmdef, Shared/...
Files:
  <path relative to the feature>   # <Feature files row>
Open questions:
  none | <question>
Notes:
  <free text>
```

- Cada `Decisions` toma un valor de la lista. Un caso que la lista no cubre va a `Open questions` y se le pregunta al usuario.
- `outside-feature` obliga a declarar de antemano todo cambio fuera de la carpeta del feature (lo de `Unity.Localization` en la corrida 2). Lo que no esté declarado, el verificador lo marca.
- `TASK-01`/`TEST-13`: la misma pregunta de aprobación incluye el plan, como ahora.

**`architecture/workflow/checklist.md`**: ítem 13 se amplía con "¿coincide lo entregado con `Logs/ai/plan.md`?".

**`templates/claude/hooks/verify-on-stop.sh`**: borra `Logs/ai/plan.md` cuando la tarea termina limpia, para que el plan de la siguiente tarea no se mezcle (opcional: moverlo a `Logs/ai/plans/<fecha>-<feature>.md` como historial).

### Criterio de aceptación
- Dos corridas del inventario producen dos `plan.md` idénticos salvo `Notes`.

## F4. Assets de datos: spec y herramienta

**Por qué:** las dos corridas dejaron `{Feature}Config.asset` sin crear, porque `EDIT-06` prohíbe escribir YAML a mano y el alcance era "solo código". El installer ya lo registra, así que la generación de Fast IoC falla hasta que alguien lo cree.

### Cambios en reglas

**`architecture/workflow/planning.md`, `TASK-02`**: "Los assets de datos (configuración, catálogos) son parte del código, no de los prefabs: se crean en todo alcance".

**`architecture/EDITOR_TOOLS.md`**, regla nueva `EDIT-14`: "Un asset de datos se describe en un spec JSON junto a él, `Services/{Feature}Config.asset.json`, con el tipo y los valores. Con `editorBridge`, el agente lo construye con `AssetSpecs.Build`. Sin bridge, `verify.sh` construye los specs que no tienen asset. Nunca se escribe el `.asset` a mano (`EDIT-06`)".

### Código nuevo en el package de Unity (`unity/Editor/`)

| Archivo | Contenido |
|---|---|
| `AssetSpec.cs` | modelo del spec: `type` (nombre completo del ScriptableObject), `values` (objeto JSON con los campos serializados) |
| `AssetSpecs.cs` | `Build(string specPath)`: crea o actualiza el asset con `ScriptableObject.CreateInstance` + `JsonUtility.FromJsonOverwrite`, lo guarda junto al spec, devuelve la lista de errores. `BuildMissing()`: construye todos los specs bajo `Assets/Client` sin asset. `Compare(specPath)`: diferencias entre el spec y el asset |
| `AssetSpecCommands.cs` | menú **Assets > Unity Architecture > Build Asset From Spec**, como el de prefabs |
| `Tests/AssetSpecsTests.cs` | crear, actualizar, tipo inexistente, campo inexistente |

### Scripts

**`templates/scripts/verify.sh`**: después de compilar y antes de revisar la generación de Fast IoC, ejecuta `-executeMethod UnityArchitecture.AssetSpecs.BuildMissingFromCommandLine`.

**`templates/scripts/verify-editor.sh`**: si hay specs sin asset, le pide al agente construirlos con el bridge (mismo patrón que el validador de prefabs con el Editor abierto).

### Docs
- `architecture/PREFABS.md`: una línea que lleva a `EDIT-14` para los assets de datos.
- `docs/REFERENCE.md`: el menú y el spec.
- Rules Guide en/es: `EDIT-14`.

### Criterio de aceptación
- Corrida "solo código" del inventario: queda `Services/InventoryConfig.asset.json` y, después del Stop hook, el `.asset`. `GenerationStatus.json` sin errores.

## F5. Verificador de features en el Stop hook

**Por qué:** lo que una herramienta puede revisar no debería depender de que el agente lo recuerde.

### Script nuevo: `templates/scripts/check-feature.sh <Feature>`

Sin Unity, solo `find`, `grep` y `awk`. Cada chequeo tiene un ID y cita la regla.

| ID | Chequeo | Regla |
|---|---|---|
| `CHK-01` | Los archivos de `Files:` en `Logs/ai/plan.md` existen, y no hay archivos `.cs`, `.json`, `.md` o `.asset.json` en el feature que el plan no nombre | `PLAN-02`, `TASK-04` |
| `CHK-02` | Cambios fuera del feature (git diff) que `outside-feature` no declara | `PLAN-02` |
| `CHK-03` | Hay un `*Config.cs` o `*Catalog.cs`, un Model inyectado (un campo `internal` de un tipo `*Model` o `*Module` en una View o Controller), un Module o un Connector → existe `Services/{Feature}Installer.cs`; sin nada de eso → no existe | `DI-11` |
| `CHK-04` | Cada `Bind<X>().FromInstance("...")` tiene su `.asset` o su `.asset.json` | `EDIT-14` |
| `CHK-05` | Si hay `.cs` en `Tests/`, existe `Tests/Client.{Feature}.Tests.asmdef` con ese `name` y `rootNamespace`; no hay ningún `.asmref` | `ASM-03` |
| `CHK-06` | Hay Views y el alcance no incluye prefabs → existe `IMPLEMENTATION.md` con las 6 secciones de `HAND-07` en orden | `HAND-07` |
| `CHK-07` | Todo `namespace` es `Client.{Feature}` (o `Client.{Feature}.Tests` en `Tests/`) | `FEAT`/naming |
| `CHK-08` | `list: sectioned` en el plan → el Scroller hereda de `SectionedScroller` | `LIST-10` |
| `CHK-09` | Nombres de la tabla de F6 (View raíz de lista, header, section data, carpeta de pantalla) | `TASK-05` |
| `CHK-10` (advertencia) | Clases `static` con listas o arrays de datos dentro del feature | `MODEL-12` |

Salida: una línea por falla, `CHK-03 DI-11: Services/InventoryConfig.cs exists but there is no Services/InventoryInstaller.cs`. Código 0 si todo pasa, 1 si hay fallas (las advertencias no fallan).

### Integración

**`templates/claude/hooks/verify-on-stop.sh`**
- Después de calcular `SCOPED` (las features tocadas), y antes de llamar a `verify.sh`/`verify-editor.sh`, corre `check-feature.sh` para cada feature tocada.
- Si falla, devuelve las fallas al agente con el mismo mecanismo de bloqueo que la compilación, y cuenta para el límite de 3 intentos.
- Va antes de Unity porque es instantáneo y evita compilar algo que igual se va a rechazar.

**`templates/scripts/install.sh`**: copiar `check-feature.sh`.

### Pruebas
- `tools/test-check-feature.sh` (nuevo): `tools/fixtures/features/` con una carpeta correcta y una por cada falla (`MissingInstaller/`, `AsmrefTests/`, `NoImplementation/`, `ExtraFile/`...). El test espera exactamente el `CHK` correspondiente en cada una.

### Docs
- `architecture/EDITOR_TOOLS.md`, "Automatic verification": el hook también corre el verificador de features.
- `docs/USAGE.md`, "The Stop hook's messages": ejemplos de mensajes `CHK`.
- Rules Guide en/es.

### Criterio de aceptación
- Cada fixture falla con su `CHK` y solo con ese. El feature correcto pasa. En una corrida real, sacar el installer a propósito hace que el hook lo devuelva.

## F8. Evaluación repetible

**Por qué:** la línea base se hizo a mano con un script temporal. Para comparar versiones, tiene que ser una herramienta.

### Archivos nuevos en `tools/eval/`
| Archivo | Contenido |
|---|---|
| `prompts/inventory.txt` | el prompt de la línea base, con `{{FEATURE}}` |
| `prompts/player-health.txt` | "muestra la vida del jugador", solo código + tests |
| `prompts/settings-toggle.txt` | un toggle de settings con drag/click, código + tests |
| `run.sh` | por prompt y corrida: copia el estado del proyecto, corre `claude -p --permission-mode auto --output-format json --max-budget-usd N`, guarda timing, archivos, `plan.md`, salida de `check-feature.sh` y costo, y restaura el estado. Es lo mismo que hizo la línea base, pero dentro del repo |
| `report.sh` | junta las corridas en `docs/benchmarks/<versión>.md`: tabla de tiempos, la línea `before-first-write`, archivos iguales o distintos entre corridas, fallas `CHK` |

Parámetros de `run.sh`: proyecto, prompts, número de corridas (por defecto 2) y presupuesto. Se corre a mano por versión, nunca en CI. Cuesta unos 1,4 USD por corrida del inventario, y conviene revisar el límite semanal antes de lanzarlo (la línea base perdió una corrida por eso).

### Criterio de aceptación
- `run.sh` reproduce la línea base 0.9.1 en el mismo formato.
